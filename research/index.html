A self-hosted Llama gateway with shared team memory

A small open Llama model sits between a team and an expensive closed model (Muse Spark). It answers what it can, escalates only what it must, and shares memory and processed context across the whole team, so each piece of the company's knowledge is paid for once, not once per person. Submission due Wed 4 Nov, 9:00 PM ET.

North star: “For a team sharing one codebase, the gateway matches the accuracy of sending context straight to the closed model while sending ≤10% of the closed-model tokens. It knows when not to escalate, and the shared cache cuts gateway GPU time per user as the team grows.” Spin-off of ai-os. The original single-user north star (a learned MMU on LongMemEval and LoCoMo) stays in that repo for its own paper; this project shares the idea of a cheap learned decision, applied to escalation.
01 · Architecture

Every layer removes one cost

any app / chat UI / coding agent
        │  OpenAI-compatible API · user + team identity in headers
        ▼
┌─────────────────────── Memory Gateway (self-hosted) ───────────────────────┐
│  Llama gateway (vLLM) ── shared KV cache (LMCache, permission-scoped keys) │
│        │ escalates only when needed                                        │
│        ▼                                                                   │
│  shared text memory + permissions (Postgres + pgvector, row-level security)│
└──────────────────────────────────────┬─────────────────────────────────────┘
                                       ▼
                       Muse Spark (closed, expensive)

What each layer saves

LayerRuns onCost it removes
Gateway (Llama 8B Instruct)Your GPU (Modal)Closed-model calls. Answers easy turns itself; escalates hard ones.
Shared text memoryPostgres + pgvectorClosed-model tokens. Escalations carry a compact shared summary instead of raw files or history.
Shared KV cachevLLM + LMCacheGateway GPU time and latency. Content one person's request already processed is loaded, not recomputed, for everyone with the same access.
PermissionsPostgres RLS + scoped cache keysLeaks between people. You only reach memory and cache you're allowed to read.

The decision on every turn (the learned gate)

ActionWhen
1 · Answer locallySelf-contained, easy turns.
2 · Answer locally with memoryNeeds team context, but not hard reasoning. The shared KV cache makes this fast.
3 · Escalate to Muse with compact memoryHard reasoning; Muse gets the summaries, not raw content.
4 · Escalate to Muse with raw contextRare: when exact details matter (code, numbers).

Labels come from escalation regret: run each question through the cheap and the expensive paths, and label a turn “needs escalation” when only the expensive path gets it right. Choose the threshold to minimise errors + λ · cost; sweeping λ draws the cost/accuracy curve. Requests that contain tool calls always pass straight to Muse unchanged in the hackathon version.

02 · Why Meta models

Open weights are a requirement, not a preference

1 · Closed APIs can't share attention state

A shared KV cache needs control of the model's internal state. No closed API exposes it. The cached read path has to be open weights, so it's Llama.

2 · A shared cache standardises a company on one model

A cache only works with the model that produced it. Every company that adopts a shared cache standardises on one family. This makes Llama infrastructure, not just a model choice.

3 · Open and closed split by what each does best

Llama handles the high-volume, repeated reading through the shared cache. Muse Spark handles the planning and reasoning where caching doesn't help.

Don't claim “only Meta models can do this”: Qwen or Mistral would also work technically. Claim “requires open weights; built and measured on Llama”.

03 · Security

Postgres handles who-can-read-what; the cache keys handle the timing leak

ThreatMitigation
Reading another team's memoryPostgres row-level security on every memory row, keyed by team and user.
Claiming to be someone elseEach API key maps to one team and user (only its hash is stored). Identity never comes from client-supplied headers. Usage reports and forced routes need an admin key.
Inferring cached content from response timing (shown in published attacks)Include the permission scope in every cache key, so hits only occur between people with the same access. Postgres stores which entries belong to which scope.
Private conversations leaking into shared memoryPersonal conversation memory is private by default. Only shared knowledge (codebase, docs, team decisions) goes into the team scope.
Cache files on diskTreat them as sensitive as the source code they were computed from.
04 · Evaluation

Two measurements, both objective where possible

A · Accuracy vs. closed-model tokens

  • Code: SWE-bench Lite issue localisation. Given the issue, name the files to change; the gold answer is the files in the real patch. No LLM judge needed.
  • Conversation: LoCoMo subset (LLM judge; spot-check 50 by hand).
  • Pass: within 3 points of Muse-direct at ≤10% of Muse tokens.

B · Team scaling

  • Treat SWE-bench tasks on the same repo (e.g. Django) as different engineers.
  • Replay them with 1, 2, 4, 8, 16 simulated users.
  • Plot gateway GPU-seconds and Muse tokens per user against team size. Sharing works if the curve falls.
  • Tasks span different commits, so cache invalidation gets tested for free.

Baselines (same questions, same models)

BaselineWhat it tests

Llama-onlyThe floor: never escalate.
Gateway + rule-based escalationIs learning the gate worth it?
Gateway, no sharingIsolates the team-sharing gain.
Full gateway (learned gate + shared memory + shared cache)The contribution.

08 · Deliverables

A gateway, not a harness

A harness runs a model with tools (Claude Code, Cursor). A gateway sits between any harness and the models, so it works with every harness instead of competing with them.
